# QA fuzz / robustness report (QAP-08, SEC-001 automated part)

**Owner:** QAP · **Date:** 2026-10-09 · **Evidence:** AUTO, HOST CPU (x86_64 container, 4 vCPU).
This is a deterministic **mutation smoke fuzzer**, not a coverage-guided fuzzer (no cargo-fuzz/AFL
in this environment). It finds panics, timeouts and heap blow-ups near the seed corpus; it does not
prove absence of bugs. SEC review of the result is still required (SEC-001 is PARTIAL).

## 1. What runs

* Harness: `crates/veskra-qa/tests/fuzz_smoke.rs` (`fuzz_smoke_all_targets`).
* Seeds: `tests/fuzz-corpus/` (18 seed files, ~60 KB, all generated by Veskra; provenance in its README).
  Regeneration is deterministic: two runs of `VESKRA_REGEN_FUZZ_CORPUS=1 cargo test -p veskra-qa --test fuzz_smoke corpus`
  gave byte-identical files (`sha256sum -c`).
* Mutations (`veskra_testkit::Rng`, fixed seeds per target): 1–8 bit flips, interesting-byte
  overwrites, truncation, splices from other seeds, chunk duplication, length-field inflation
  (u16/u32 BE/LE with 0, 0x7F, 0xFFFF, 0x7FFFFFFF, 0xFFFFFFFF, 2·len, …), stacked 1–4×; JSON
  structural mutations for commands and for bundle entries.
* Structure-aware `.veskra` target: unzip with `veskra_format::zip::ZipReader`, mutate one or two
  entries (JSON structurally; tiles/strokes/ICC/preview bytewise), re-zip with `ZipWriter` and a
  **recomputed `integrity.json`**, so mutations get past the SHA-256 check; documents that decode
  are then composited (`thumbnail_rgba8`) and re-encoded.
* Command target: paths are rewritten into `target/qa/fuzz/sandbox/`, and `document.create` is
  clamped to ≤ 1024 px per edge **by the harness** (the engine itself allows 8192²).
* Per-input assertions: no panic (`catch_unwind`; input saved to `target/qa/fuzz/crashes-<N>/`),
  wall time ≤ 5000 ms, peak heap growth ≤ 512 MiB, measured by a counting global allocator in the
  test binary only (the only `unsafe` in `veskra-qa`, documented in the file; needs QAP + ORCH
  review per AGENTS.md §5). The slowest and heaviest input of each target is always saved.

Commands:
```sh
cargo test -p veskra-qa --test fuzz_smoke                                  # default 1000/target
VESKRA_FUZZ_ITERS=20000 cargo test --release -p veskra-qa --test fuzz_smoke fuzz_smoke_all -- --nocapture
```
Default run (test profile, 1000 iterations per target): **9 000 inputs, 0 panics, 5.96 s**.

## 3. Finding QA-D3 — far off-canvas stroke coordinates are bounded but very expensive (P2, robustness)

The slowest/heaviest input (`target/qa/fuzz/crashes-20000/input-heaviest.bin`) is a packed stylus
batch whose `MOVE` events carry finite but huge view coordinates (x = 5.1e7, −2.1e14, 1.0e36, …).
`unpack_events` accepts any finite value; the brush drops samples beyond `MAX_SAMPLE_COORD = 1e6`
and caps dabs at `MAX_DABS_PER_STROKE = 8 000 000`, so the cost is **bounded** — but the bound is
independent of the canvas size. Minimal reproducer (release CLI, measured here):

```text
{"cmd":"document.create","width":128,"height":96,"background":"#FFFFFF"}
{"cmd":"brush.select","preset":"pen.brush"}
{"cmd":"stroke.begin"}
{"cmd":"stroke.samples","samples":[{"x":10,"y":10,"t":0,"p":0.5},{"x":1e6,"y":20,"t":4000000,"p":0.5}]}
{"cmd":"stroke.commit"}
```
| far x | wall | peak RSS |
|---|---|---|
| 1e4 | 0.03 s | 11 MiB |
| 1e5 | 0.21 s | 23 MiB |
| 1e6 | 1.59 s | 145 MiB |
| 3e6 / 1e7 | 0.00 s (sample dropped) | 11 MiB |

One 2-sample stroke on a 128×96 canvas costs 1.6 s and 145 MiB on this host CPU; a device is
slower and memory-constrained, and this runs on the input path. **Route:** BRH (`veskra-brush`
renderer: do not generate/store dabs for segment parts farther than the brush radius outside
the canvas/clip) and AND (`veskra-input::unpack_events`/arbiter: reject or clamp view
coordinates outside a plausible range, e.g. ±4× view size). Not a crash; no data loss.

## 4. Limits of this evidence

* Host CPU only; heap limits are measured with a counting allocator, not an OS sandbox/rlimit.
* Not coverage-guided; seeds are Veskra's own outputs. No third-party PSD/SVG/PDF/ICC files
  (the CLR report's local Krita ICC corpus run is separate and not committed).
* Exporter `validate` functions are Veskra's own structural readers, used only to re-check
  Veskra output; the PNG **import** path (`veskra-io::import`, added concurrently by another agent)
  has its own `sec001_mutation_loop_no_panic` test and is not part of this harness yet.
* SEC-001 remains **PARTIAL** until a security reviewer accepts the limits and QA-D3 is resolved.
